# Skins — customizing the GitHub README without breaking the engine

The `github-readme` renderer is deterministic and fixed-order **by contract**:
same SSOT, same bytes (profile-as-code SPEC §15.3; the engine is pinned in
`.pascorc`). A **skin** is the contract-safe way to make the profile distinctive
without giving that guarantee up: you write a **variant body** — a complete
README — and `pasco build` publishes it verbatim.

Cubre: the GitHub profile README (`profiles/github-readme/`) · No cubre: the
renderer itself, other platforms, or auto-updating widgets · as_of: 2026-11-03.

## The bound: what the engine judges

`pasco build` writes the artifact, but the consistency checks do not read the
whole file. They project it to the **engine-owned region**
(`packages/artifact`, SPEC §19.5): from the **last H1 above the terminus** to the
**last generated footer**.

```text
preamble chrome         ← outside the region: your visual identity, not judged
────────────────────────────────────────────────────────────────────────
# Alex Rivera            ← the last H1 above the footer opens the region
… facts from content/ …  ← inside: every fact must agree with the SSOT
<!-- generated by … -->  ← the terminus: the last generated footer closes it
────────────────────────────────────────────────────────────────────────
appendix chrome         ← outside the region: not judged
```

The terminus is this exact line, with the counts the build produced:

```text
<!-- generated by profile-as-code pasco build github-readme · N projects · M publications -->
```

The renderer pluralizes those counts: at one it writes `1 project` /
`1 publication`. Copy the line the build actually emitted, not the template above.

The contract in one sentence: **keep the H1 and the generated footer, put your
visual identity outside them, and never retype a fact inside them.**

## What the engine guarantees

Three facts read from the engine source, not from its documentation (engine
0.3.7, the pin in `.pascorc`):

1. **The active variant body is written verbatim.** `pasco build github-readme`
   writes `profiles/github-readme/variants/<id>.md` as the whole artifact when
   `content/active.yaml` selects it for that lang
   (`packages/cli/src/variant-store.ts` · `artifact-render.ts`; SPEC §7/§15).
   The body is a *complete README*, not a fragment.
2. **The artifact is bounded, not whole.** The projection
   (`packages/artifact`, SPEC §19.5) opens the engine-owned region at the last H1
   above the terminus and closes it at the last generated footer.
3. **That bound is what makes chrome legal.** `fact-present` — the symmetric
   surface-vs-SSOT comparison — runs over the projection only. Chrome outside it
   survives every check; content inside it is drift if it disagrees with the
   SSOT. With an active variant body the comparison is against that same body,
   so read the declared limit below before trusting it as a fact check.

## The mechanic

```bash
# 1. Write a COMPLETE README body (the exemplars below are complete bodies).
profiles/github-readme/variants/<id>.md

# 2. Record the choice; this writes content/active.yaml.
pasco refine github-readme --choose <id>

# 3. Publish the chosen body verbatim.
pasco build github-readme
```

`pasco refine` without `--choose` prints the agent task template; it makes no
model call and no network request. `--choose` records the pick only. The body is
workspace input: the engine never writes or edits it.

## Do / don't

| Allowed outside the bound | Forbidden anywhere |
|---|---|
| Banner image and a tagline | scripts, visitor counters, typing animations |
| Static `shields.io` badges (4–6, from `identity.links`) | snake games, external trackers |
| `<details>` blocks for secondary material | facts retyped by hand inside the region |
| At most one stats card | a claim no `content/` row carries |

Even when a URL is outside the projected region, source it from
`identity.links` where the fact exists — the engine skill's golden rule (URLs
only from the SSOT) is still the discipline; see the declared limits for why the
machine does not enforce it yet.

## Refresh ritual: the skin is a snapshot

The variant body is input, not a live view. After `content/` changes the README
does **not** update itself: `pasco build` still writes your body verbatim, so the
facts inside the region can go stale while the build stays green. Re-read the
changed rows, recompose the body, then rebuild.

`pasco status` will and will not tell you:

- **Will** — the ledger `sync` state (`stale` after `content/` moved since the
  last `pasco status --mark`, `never`, `in-sync`) and the artifact axis.
- **Will not** — whether a fact inside the region is current. While a variant
  body is active the artifact axis compares the body against *itself* (declared
  limit below), so `matches-SSOT` is not a fact check on the skin.

## Declared limits (discover them here, not in production)

- **Self-comparison.** While a variant body is active, `fact-present` compares
  the artifact against that same body: the skin is **trusted input, not rendered
  output**. Drift inside the region is not caught by the artifact axis; the
  discipline is on the author.
- **SSOT staleness on that surface is tracked by the ledger**, not by the
  artifact axis: `pasco status` derives it from the ledger `contentHash`.
- **No marker, no bound.** If the generated footer is missing,
  `projectArtifact` falls back to the last H1 → end of file, silently pulling
  appendix chrome into the bound; `pasco build`, `pasco check` and `pasco status`
  still pass. The marker is a contract, not a gate: keep the footer or the bound
  collapses.
- **`link-in-identity` is declared, not executed.** The rule is declared in the
  engine's `skills/github-readme/checks.yaml`, but `pasco check` does not execute
  it in this release (the remaining catalog lands with M3/M4). Extra image URLs
  in the skin are not machine-checked yet, so the discipline is on the author.

## Exemplars

Three complete bodies over this workspace's fictional example data, one per

the generated footer, and rebuild.

| File | Composition | Chrome |

Each file opens with a one-line HTML comment naming the composition, the chrome
sources and the date. The comment is invisible in GitHub's rendered view and sits
outside the bound.

## Adopt one

1. Copy the exemplar body to `profiles/github-readme/variants/<id>.md`.
2. Replace the chrome with your own (keep the H1 and the footer).
3. `pasco refine github-readme --choose <id>`.
4. `pasco build github-readme`.
5. Deploy, then run the GitHub line in `CHECKLIST.md`.

No engine change, no fork, no new schema field. Do not vendor someone else's
README: imported prose, links and license are a provenance problem, and they
contradict the restraint rule.
